# AI 建议与人工判断

开发过程中模型给过不少实现建议。下面只记对产品形状有影响的条目：建议原文大意、是否采纳、判断理由。不少于 5 条。

| # | AI 建议 | 判断 | 说明 |
|---|---------|------|------|
| 1 | 统计图用 ECharts / Chart.js，少写 SVG | **不采纳** | 需求与 `docs/frontend-design.md` 写明不上图表库。环/柱/横条数据量固定，原生 SVG + HTML 足够，也避免前端镜像再拉一套库。 |
| 2 | 前端对当前列表 `items` 做 reduce 当看板数字 | **不采纳** | `page_size` 上限 100，列表不是全库。看板必须读 `GET /api/stats`，且**不**随列表筛选变化。 |
| 3 | 按设计稿拆掉四张 KPI 卡，改成冷灰工单台、黄签只表示 high | **不采纳（配色与 KPI）；部分采纳（三种图）** | 当时页面已经是灰蓝绿玻璃卡 + 左侧导航，推倒会和已上线工作台不一致。看板保留 KPI 卡，图贴现有颜色。三种图同时出现、点图只改一个筛选，这一点按设计做了。 |
| 4 | 编辑任务走 `PUT`，和「全量更新」文档一致 | **不采纳** | 约定 PUT 省略 `description` 即清空。页面没有单独的「清空描述」控件，误用 PUT 会丢字段。前端保存走 `PATCH`；PUT 仍保留并用测试锁住行为。 |
| 5 | 第一次做列表时就把 `/api/stats` 做成 `priority` + `assignees` | **先采纳，阶段上又收回，看板阶段再采纳** | 工单台早期提交里扩展过统计。随后按「本期只要四项状态计数」改回（`a1e0594`），避免接口超前于页面。看板要画柱和排行时再加回字段，并补测试与 `docs/api.md`。 |
| 6 | 点图留在看板，只高亮图例；列表在另一页不同步 | **不采纳** | 用户选定：点环/柱/具名横条跳 `#workbench`，只改对应筛选，`page=1`。再点同一项回到「全部」。点「其余」不跳。 |
| 7 | 时间段、部门、导出、KPI 副文案用假数据把页面填满 | **不采纳** | 需求明确不做按过滤条件变化的统计，也没有部门模型。假数字会和真实 KPI 打架。这些控件保持 disabled +「后续接入」。 |
| 8 | 后端用 `requirements.txt` + pip，测试连 Docker 里的 Postgres | **不采纳** | 计划已定 uv（`pyproject.toml` + `uv.lock`）。测试用 SQLite 内存库，才能在没起容器时跑 `uv run pytest`。 |
| 9 | 引入 Alembic，从第一天做迁移 | **不采纳** | 本期两张表、允许 `create_all`。迁移不在范围里；上线后若要改表结构再另开。 |

人工侧额外约束（不是模型主动建议，但是否决过模型默认行为）：Git 提交说明不要带 `Co-authored-by: Cursor`，GitHub 上只显示仓库作者。
